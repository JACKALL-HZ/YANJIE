# 统一推演流程设计

## 目标

所有决策场景使用同一套面向用户的推演流程，同时保留各场景自己的规则计算方式。
体验上要支持自然语言决策，让智能体分析和建议随上下文变化而变化，并将已确认的
个人画像快照作为推演起始条件。

## 产品规则

1. 用户先提供决策事实，也可以补充个人画像。
2. 系统返回已收集信息的摘要，用户确认后才创建推演会话。
3. 系统根据确认的信息和冻结的画像快照生成结构化初步分析，但不推进推演年份。
4. 市场、环境、个人、风险四个智能体接收同一份初步分析和各自的角色证据。启用 MCP
   时调用相应工具；工具不可用时明确展示证据状态，不能编造外部事实。
5. 智能体需要展示自己的判断、依据、备选方案和反对意见。出现实质分歧时，进入一次
   有上限的裁决与修订，并向用户展示博弈记录。
6. 每个推演年度开始前，包括第 1 年，用户先提交自己的决策；智能体据此分析，规则
   引擎结算该年度，随后请求下一年的决策。
7. 风险干预和年限确认是独立输入，不能与年度决策共用含义模糊的暂停状态。

## 状态协议

接口保持稳定的 `phase`，并返回更具体的 `input_kind` 与 `pause_reason`。

| 状态 | 期望的用户输入 | 处理结果 |
| --- | --- | --- |
| `input_confirmation` | 确认或修正事实、画像 | 生成初步分析 |
| `year_decision_required` | 自然语言年度决策 | 生成方案预览或进入年度分析 |
| `decision_preview_required` | 选择一个生成的方案 | 应用可审计的已确认影响 |
| `intervention_required` | 选择声明的风险干预选项 | 处理风险干预 |
| `horizon_review` | 延长推演或完成结算 | 修改年限或生成最终结算 |
| `completed` | 无 | 返回评分和行动计划 |

为兼容已有接口，过渡期可以保留 `paused` 作为 `phase`，但必须同时返回
`pause_reason`。前端必须据此展示控件，不能把所有暂停都当成“年度经营决策”。

## 灵活决策

系统先将用户的自然语言理解为带有置信度和解释的结构化意图。若能安全映射到场景中
声明的动作效果，则使用该效果；若无法安全映射，则生成方案预览，说明系统理解、前提、
取舍、替代方案和仍需补充的信息。

新想法不得在未确认时悄悄修改数值世界状态；只有用户确认的映射动作或场景声明动作
才能影响数值。决策源始终负责动作效果、结束条件和评分计算；大模型只负责理解、生成
和解释，不能自行决定数值结局。

## 个人画像快照

推演开始时，将用户确认的画像复制为会话快照，后续修改画像不会影响这次已开始的推演。
四个智能体都使用经过最小化处理的画像摘要。时间、收入稳定性、现金缓冲、技能、可用
资源、家庭约束和风险承受能力等因素，会影响初步分析、初始约束、年度建议、风险阈值和
评分解读。缺失字段必须采用明确的保守假设。

## 动态世界状态

世界状态不能是所有场景共用的一组固定展示字段。它分为三层：

- 通用状态：当前年份、目标进度、资源余量、风险暴露和执行能力。
- 场景状态：由决策源声明，例如创业使用现金流、客流和回本进度；求职使用能力匹配、
  面试机会和求职周期；投资使用仓位、回撤和流动性。
- 用户修正项：用户填写的决策事实和个人画像调整对应指标的初值、阈值与年度变化幅度。

状态初始化遵循“场景默认值 + 已确认用户信息 + 画像修正项”的顺序。年度决策和 MCP
证据只能经由场景规则引擎转换为状态变化；大模型不得直接写入任意数值。前端根据场景
状态定义展示相关指标，缺失或不适用指标不显示。

## 实施范围

本次优化包含共享的 API 状态协议和状态恢复、引擎事件顺序、意图理解与方案预览、以及
前端按输入类型引导。各场景现有的结算引擎保留在统一年度流程之后，不做无关重写。

## 测试策略

- 每个支持场景均覆盖：初步分析、第 1 年决策、年度结算、下一年决策和年限确认。
- 验证画像快照传递给四个智能体，且后续编辑画像不会改变已开始的推演。
- 验证相同场景在不同用户事实、技能、时间和风险偏好下，初始世界状态及对应指标会
  产生可解释的差异。
- 验证无法直接映射的自然语言决策返回方案预览或针对性追问，不再返回笼统的 422 错误。
- 验证每种暂停原因只接受对应输入；输入不匹配时必须保持原状态。
